<why_the_apex_is_not_evidence>
**Read this before running anything.**

Each milestone's apex carries a harness re-run check guarded by the nested flag: when the flag is set,
the check skips with a note about not re-running against an evolved corpus. The apex sets that flag on
**every** child. The six checks that would run the six converted harnesses therefore all skip inside
any apex run.

The consequence is exact: a perfect apex triple is fully compatible with all six conversions being
broken. And the per-harness anti-vacuous-green guards authored in the conversion plans live *inside*
those six programs — so they are never executed by the apex either.

The only instrument that exercises the deliverable is six direct invocations. That is this plan.

**The second-order asymmetry, recorded once so the next milestone does not re-litigate it:** the
nested guard's stated rationale is avoiding a re-run against an *evolved* corpus. The conversion
destroys that rationale — the corpus each harness reads is now frozen, so a re-run would be identical.
But the five predecessor apex validators carrying that rationale are frozen surfaces and cannot be
edited, so the benefit of the conversion is permanently invisible to the apex. Write it down.
</why_the_apex_is_not_evidence>
