<objective>
Prove the milestone's claimed fixes against git, and account for every difference between the structural
gate's two halves.

This is the plan the phase's requirement is named after. Everything before it produced a corpus; this
produces the evidence that the corpus is what the milestone said it is. Two properties make that
evidence real rather than ceremonial: the audit runs at the final content revision so no row is asserted
against a corpus that later moves, and the unattributed drift count is computed by a tool with per-row
evidence rather than typed as zero by the person who wants it to be zero.

The drift half is deliberately not a second measurement pass. The gates were measured once in plan
158-01 and are measured once here; re-executing them in a purpose-built second tool would prove only
that they are deterministic, at the cost of several minutes and a fourth tool this milestone would then
have to justify.

Ordering: D-69 constraint 5 puts the binding audit at the final content revision after every corpus
edit; D-69 constraint 6 puts the after half at that same revision, on a clean tree, before the bundle.

Purpose: discharge the claimed-fix requirement and the drift-accounting criterion with artifacts a
stranger could re-run.
Output: the full audit row population with its run log, and the completed gate baseline with its drift
rows, its unattributed count and both discharge records.
</objective>

**Population.** Author one row per claim across all seven surfaces the discovery run enumerated. For the
six fix commits that touch no corpus file, set `evidence_path` to the path the claim is actually about,
distinct from the commit's own path — otherwise the row asserts nothing about the claim.

Classify every "corrected to a value" claim:
- Corpus-consistency rows assert what the corpus can prove. The citation-date family asserts the count
  of dated citations of the same article and the absence of the superseded date outside the review key.
  The group-count family asserts the counts of the two disambiguated phrases and the absence of the
  ambiguous one. The hub-link family uses the four site-scoped needles, because both the link-present
  needle and the platform-count needle are false at the unfixed corpus and either alone would pass on it.
- External-fact rows name the prior phase's rendered-bytes method and its control page as their
  verification and assert nothing about the live page. Do not re-fetch: a re-fetch is a new measurement,
  and a vendor page's own date field can legitimately move.
- Replacement rows carry a needle for the removed text; the replacement text gets its own row.

**This phase's own remediation.** Every edit plans 158-02 and 158-03 landed is also a row. Assert an
additive change through absence at the parent or an increased count. Where the old line is a prefix of
the new one — the skill document's corrected invocation is the case — use a full-line needle, because a
prefix needle is present at both ends and the row would be vacuous.

**Not by the runner.** The planning-document amendments in plan 158-07 are asserted by the three
planning-tree validators, not here. Do not author rows for them.

**Secret rows.** Any row about the scrub carries a null needle and a redacted claim. Its evidence is the
row's own path at its own fix revision, requiring exactly one removed content line there; two or none is
a loud failure rather than a tiebreak — the scrub commit has two changed files with one removed content
line each and only one of them carries the value, so a novelty tiebreak picks the wrong file. Do not run
the pickaxe for such a row: a marker on a process's argument list has already been observed in this
repository's process table.

**Run and record.** Run the audit. Every row must PASS and no row may be vacuous. Write the run log with
the row-set hash as its first line and with the run's revision stated as the **parent** of the commit
that will record it. Head equality is unsatisfiable here by construction — the close-out sequence appends
commits after any revision the phase records — so state the parent relationship rather than an equality
that will be false the moment the commit lands.

**Negative control before committing.** Recover the removed value into memory only, by the scoped
recovery. Grep every artifact of this phase for it and require zero. Then apply the same grep to an
in-memory string built to contain it and require one hit. Never write the value to disk, never place it
on a command line, and never run the pickaxe for it.

Apply, gate and commit in one tool invocation.
