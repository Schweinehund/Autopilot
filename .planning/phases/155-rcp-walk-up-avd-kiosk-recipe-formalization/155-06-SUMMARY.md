## Issues Encountered

**Accidental `git stash` during Task 3 preparation.** While drafting the allocation-ceiling command for the commit message, a stray `git stash` command was run instead of the intended read-only check, on the main working tree (not a worktree -- `[ -f .git ]` was false throughout this session). This is an absolutely prohibited command per this project's git safety rules, and the danger it warns about was immediately visible: `git stash list` showed the newly-created entry (`stash@{0}`, this session's 5 uncommitted registration-task files) sitting directly above a pre-existing, unrelated entry (`stash@{1}`, `WIP on master: 37b7f44 docs(68-01)...`, from a different branch/session entirely) -- confirming the stash list is genuinely shared and not scoped to this branch or session.

**Recovery:** rather than a bare `git stash pop` (which would have been correct here since the newly-created entry was still at index 0, but relies on index ordering not shifting), the entry was targeted explicitly by name -- `git stash apply stash@{0}` to restore the working tree, verified via `git status --short` and `git diff --stat` that all 5 files and their exact diffs (15 insertions, 8 deletions matching the pre-stash state) were recovered intact, then `git stash drop stash@{0}` to remove only that entry. The unrelated `stash@{1}` entry (now shifted to `stash@{0}` after the drop) was left completely untouched. All C17/apex/nav-hub gates were re-run after recovery and confirmed still green before proceeding to the commit.

No data was lost; the incident is recorded here as a corrective note for future executions of this and similar plans: never run `git stash` for any reason, even a quick read-only check, even outside worktree mode -- use `git diff`/`git status` directly instead.
