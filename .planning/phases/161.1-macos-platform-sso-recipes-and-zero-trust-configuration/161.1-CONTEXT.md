# Phase 161.1: macOS Platform SSO Recipes and Zero-Trust Configuration - Context

**Gathered:** 2026-11-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Three new Device Recipes under `docs/recipes/`, plus the wiring, registry, requirement IDs and validator that make them first-class corpus documents:

1. A device recipe whose end state is an ADE-enrolled Mac registered for Platform SSO (PSSO) with the passwordless Secure Enclave key method.
2. A device recipe whose end state is an ADE-enrolled Mac registered for PSSO with the password-sync method, framed as the fallback.
3. A tenant-configuration recipe (STD-05 D-08 form) whose end state is a tenant where macOS access to all resources requires a compliant device, with phishing-resistant authentication strength for Secure Enclave users.

The recipes build on RE-123, RE-124 and RE-205; they do not replace them. Corrections to those guides are in scope only where re-verification proves a claim wrong (D-38). Inserted urgently after Phase 161 on 2026-11-18 at the owner's request; Phase 161 plan 161-04 is still owed and the phase pointer in STATE.md was deliberately left on 161.

<decisions>
## Implementation Decisions

### Recipe shape
- **D-01:** Two separate device recipes, one per PSSO method, each with its own STD-05 D-06 one-line end-state Summary and its own Verification section. -- **Reversibility:** costly -- once published, inbound links, registry rows and the validator all name three documents; merging later rewrites all of them.
- **D-02:** Zero trust is its own tenant-configuration recipe in the STD-05 D-08 form. Both device recipes link to it; it does not repeat their device steps.
- **D-03:** The password-sync recipe is framed as the fallback. The Secure Enclave key is the default (RE-124 records it as Microsoft's recommendation); a decision block near the top sends readers who qualify for Secure Enclave to that recipe. Audience reasons are legacy hardware and organizations not ready for passwordless, subject to D-15.
- **D-04:** Each device recipe carries the full ordered Settings Catalog steps (every field and value the build needs) so it runs end to end on one page. Rationale, the dual-field explanation and failure trees stay in RE-123 and RE-124 behind links.
- **D-05:** Smart card gets a single line in the Secure Enclave recipe's method decision block pointing to RE-124's Smart Card Method section. No smart-card recipe.
- **D-06:** One primary user per Mac. New User At Login Window (NUAL) and shared Macs get a pointer only.
- **D-07:** The zero-trust recipe is macOS-only, sectioned (compliance, Conditional Access, rollout) so iOS and Windows sections can be added later without restructuring.
- **D-08:** End-state titles matching recipes 01-06, for example "Mac with Passwordless Platform SSO: Secure Enclave Key Provisioning". The planner drafts the final titles in that pattern.
- **D-09:** Rollback/Recovery is an undo ladder, least destructive first: unassign the policy, remove the PSSO registration on the device, then wipe and re-enroll (link RE-123's Recovery section). Each rung states what is lost, including the Secure Enclave key and affected keychain items.
- **D-10:** Inbound wiring from all four surfaces: the `docs/index.md` recipe table, See Also entries in `docs/admin-setup-macos/00-overview.md` plus RE-123 and RE-124, the Conditional Access Cross-Reference in `docs/admin-setup-macos/05-compliance-policy.md` (zero-trust recipe), and `docs/decision-trees/06-macos-triage.md` (known-good build).
- **D-11:** Each device recipe has a short section on what the user sees during Setup Assistant and first sign-in, linking RE-123's End-User Sign-In Experience section. Frontmatter stays `audience: admin`; no separate end-user handout.

### Starting point and floor
- **D-12:** Path A2 (PSSO registration during Setup Assistant) is the main path, matching RE-123's chosen configuration. A STD-05 decision block branches to path A1 (post-enrollment registration through the Registration Required notification) for fleets below macOS 26.
- **D-13:** OS floor is set per path. A2 requires macOS 26 or later (hard gate). The A1 branch requires macOS 15.3 or later, avoiding the 15.0-15.2 re-registration loop RE-123 records. macOS 13 and 14 are noted as Microsoft-supported but not covered by these recipes.
- **D-14:** On the password-sync recipe's A2 path, PSSO creates the first local account (`Enable Create First User During Setup`). This is the capability only the Password method has, so the recipe demonstrates it.
- **D-15:** Research checks Apple's macOS 15.3 and macOS 26 compatibility lists against Macs without a T2 chip. If no non-T2 Mac meets the D-13 floors, the password-sync recipe's audience is reframed to organizations not ready for passwordless, and the legacy-hardware case points to RE-124 instead of claiming the recipe serves it.
- **D-16:** Starting state is Apple Business Manager configured, an ADE token synced to Intune and Macs assigned to the MDM server, linking `docs/admin-setup-macos/01-abm-configuration.md`. Each recipe builds the ADE enrollment profile itself, because A2 depends on specific profile settings (user affinity, Setup Assistant with modern authentication, Await final configuration = Yes, Locked enrollment = Yes).
- **D-17:** Each device recipe enables FileVault and escrows the recovery key to Intune, because FileVault interacts differently with each method (RE-124 FileVault sections; the Password method's FileVault Policy on macOS 15+). The zero-trust recipe only checks encryption through compliance.
- **D-18:** Company Portal is sourced from Microsoft's official macOS .pkg download. The admin confirms version 5.2604.0 or later before uploading it as a macOS LOB app, with only `com.microsoft.CompanyPortalMac` in the app bundle ID list, per RE-123. Not VPP.
- **D-19:** The Secure Enclave recipe is built and verified for Apple Silicon. Intel Macs with a T2 chip that can run the D-13 floor are listed as supported, with exact models confirmed by research.
- **D-20:** The Touch ID policy for the PSSO key is a STD-05 decision block: no biometric requirement (default) versus requiring Touch ID or the Mac password. Each branch states what the user sees and the effect on Macs without a Touch ID sensor.

### Zero-trust strictness
- **D-21:** Two Conditional Access policies. Policy 1 requires a compliant device for macOS on all resources. Policy 2 requires phishing-resistant authentication strength for users on Secure Enclave Macs; password-sync users get standard MFA strength, because password sync is not phishing-resistant (RE-124).
- **D-22:** Rollout runs report-only, then sign-in log review for would-be blocks, then a pilot group, then all users. Break-glass emergency-access accounts are excluded from every policy, and the recipe has the admin confirm that exclusion first.
- **D-23:** DF-9 (RE-123 Known Silent Blockers: a compliant-device policy blocks PSSO user registration on newly enrolled Macs) is re-verified against current Microsoft Learn before any design depends on it, including whether it applies on A2 and which Intune and Company Portal apps are already exempt. If it holds, the recipe builds a named enrolling-Macs exclusion group with an explicit removal step and a verification check. If it does not hold, there is no exclusion and RE-123 is corrected under D-38.
- **D-24:** Compliance baseline: FileVault required, minimum OS matching the D-13 floors, firewall on, SIP required, Gatekeeper set to Mac App Store and identified developers. Each setting is paired with the profile that enforces it, per 05-compliance-policy's compliance-versus-configuration table. No password expiration, per `docs/admin-setup-macos/03-configuration-profiles.md:142`.
- **D-25:** Noncompliance actions email the user immediately and mark the Mac non-compliant after a short grace period (around one day; the planner picks the value). Links to L1 runbook 14.
- **D-26:** Conditional Access targets All resources. The only exclusions are what PSSO registration and enrollment need, as established by D-23, and every exclusion is listed with its reason.
- **D-27:** Browsers: Safari and Edge are stated to pass natively; Chrome gets the Microsoft Single Sign On extension force-installed through managed browser policy. Verification includes one sign-in test per browser. Research confirms each browser's current requirement.
- **D-28:** No session controls. Sign-in frequency is not set because it undoes the PSSO seamless sign-in. Token protection is mentioned only if research confirms macOS support.
- **D-29:** Unmanaged and personal Macs are blocked by design, and the recipe says so plainly.
- **D-30:** Blocked-user support routes to the existing L1 runbook 14 and the 06-macos-triage decision tree. The phase checks runbook 14 still matches the new policies and edits only what is now wrong.
- **D-31:** Licensing baseline is Entra ID P1 (compliant device and authentication strength). A STD-05 decision block offers sign-in-risk and user-risk policies for P2 tenants. Research confirms the licence each feature needs.
- **D-32:** Before creating policies, the recipe has the admin list existing Conditional Access policies that target macOS or all platforms and run the What If tool for a test user. It names the known conflict classes, such as an older compliant-device policy that catches PSSO registration, or legacy per-user MFA (RE-123 DF-3).

### Evidence and status
- **D-33:** The plan includes an owner `checkpoint:human-action` on a real Mac (A2 build, one browser sign-in, a Conditional Access report-only reading) with a non-halting decline, the Phase 160 and 161 precedent. On decline, each recipe states that it has not been pilot-tested, and no reading is written that was not taken.
- **D-34:** Each recipe gets an RE ID and a row in `docs/_registry/RE-index.md`, as recipes 01-06 have. Status is Approved only if the D-33 pilot ran; otherwise Draft. -- **Reversibility:** one-way -- RE IDs are a published contract cited by registry rows, frontmatter and inbound links.
- **D-35:** A small structural `check-phase-161.1` validator checks registry rows, frontmatter, the D-06 Summary opening, STD-05 decision-block shape, the four D-10 inbound links, and anchor resolution. It is wired into the apex chain so Phase 167's close re-audit covers it. It makes no claim about prose truth. -- **Reversibility:** costly -- the apex chain and Phase 167's expected counts both name it.
- **D-36:** Every Microsoft Learn and Apple claim is checked against the fetched source bytes, never a WebFetch summary. An independent fact check runs in a fresh `claude -p` process. Claims reused from RE-123, RE-124 and RE-205 are re-verified, not inherited. Then `/adversarial-review` on the finished recipes.
- **D-37:** Add three or four requirement IDs to `.planning/REQUIREMENTS.md` (for example MAC-01 Secure Enclave recipe, MAC-02 password-sync recipe, MAC-03 zero-trust recipe, MAC-04 wiring plus validator). The pinned validators (V-54-21 among them) are baselined before and after the edit, and Phase 167's expected counts are updated in this phase. -- **Reversibility:** costly -- REQUIREMENTS.md is validator-pinned and live-read at milestone close.
- **D-38:** If re-verification proves RE-123, RE-124 or RE-205 wrong, the guide is corrected in this phase in a separate plan with a Version History row, scoped to the wrong claim only. Any bulk rewording goes through `google-style-verify` per CLAUDE.md.
- **D-39:** The phase gets a Jira Story under the v1.23 Epic. Atlassian sign-in may need the REST fallback.
- **D-40:** All three recipes carry a 90-day `review_by`, matching RE-123's A2 drift note and recipes 07-10.
- **D-41:** Files are numbered next in sequence (`11-`, `12-`, `13-`) with the next free RE IDs, confirmed by research against RE-index.md, including the RE-240 and RE-241 gap.
- **D-42:** New prose is authored against the `google-style` skill under project Option 1 (all rules except sentence-case headings).
