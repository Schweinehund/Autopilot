<assumption_delta_decision>
**Primary noun:** `CHAIN_PHASES` — unchanged.
**Decision:** add-alongside. A literal `CHAIN_EXTRA = [30, 31]` sits beside the arithmetic span
rather than promoting a generalized "chain members" primary.
**Rationale:** D-11. HARN-18 and `PROJECT.md:25` both mandate that the span array stay generated by
arithmetic and never transcribed; promoting a union to the primary noun would put a hand-authored
element inside the thing that mandate protects. The sidecar keeps `CHAIN_PHASES` pure and confines
the hand-authored element to a named exception. Precedent for a hand-authored, non-contiguous
chain-membership array exists at `check-phase-60.mjs` and `check-phase-62.mjs`, both of which skip
phase 50.
**What changed:** the apex's chain membership stops being *one arithmetic span* and becomes *an
arithmetic span plus a hand-authored sidecar*. The success criterion wording that called the two
adopted validators members of the span itself is amended in Plan 01 accordingly.
**Accepted debt:** a THIRD membership source would force the promote this decision defers. So would
an apex whose span start drops to 31 or below — the dedup guard is scoped to the arithmetic array
alone and does not see the union, so a collision there would be silent. Neither condition holds
today; both are recorded rather than guarded.
</assumption_delta_decision>
