<needle_doctrine>
**Read this before writing a single needle.**

- **Durability, not scope.** The test is: would this needle go red at the first content commit of the
  next milestone and stay red forever? If yes, it is a bad needle regardless of how narrow it is. If
  no, it is a good needle regardless of how wide it is. A three-file negative fails the durability
  test just as a corpus-wide one does if a later milestone legitimately changes those three files;
  what makes a negative safe is a **ratified invariant**, not a small file count.
- **Corpus-wide negatives are permitted** where a ratified invariant backs them. Naming the invariant
  is part of writing the needle.
- **Derive at authoring time, never read at runtime.** Needles come from each phase's verification and
  summary documents. Those documents are read now, by you, and the resulting literals are baked into
  the validator. The validator itself reads only the corpus and the scripts tree.
- **Target the phase's own deliverables.** Content phases shipped documentation; the needles point at
  documentation. The predecessor milestone's script-paths-only clause belongs to a tooling milestone
  and does not carry.
- **Reconcile the arithmetic rule in writing.** Each leaf carries a comment stating that the chain
  array is empty because a lightweight leaf has no chain, that the arithmetic-generation requirement
  binds the apex, and that the empty literal is therefore not a transcription. Without this line a
  verifier can read the empty arrays as non-compliance.
- **State the gate-respawn decision in the header.** These leaves do not re-spawn corpus gates.
</needle_doctrine>
