Write the precedence rule into `143-EVIDENCE.md` as a numbered, fixed-order procedure, then apply
it to the four contested pairs. D-05 requires the planner to define the classes disjointly or state
an explicit precedence rule, because D-04 routes B and C to OPPOSITE remedies and an order-dependent
split silently picks one. This is that rule.

**The rule — evaluate in this fixed order; the FIRST branch that holds assigns the class, and every
(target-file, fragment) pair therefore belongs to exactly one class:**

1. **Class A/B — source-side link rewrite.** An anchor that already exists in the target file is a
   *semantic* match for the link's intent, judged from the link text plus the target heading's own
   text. A prefix or substring match that is not a semantic match does NOT qualify (D-06). If this
   holds, rewrite the source fragment to that existing anchor.
2. **Class C — target-side `<a id>`.** No semantic match exists under rule 1, but the fragment names
   a **content** row that exists in a table in the target file: the row's key cell carries the
   fragment's token, hyphen-exact, on a non-fence-masked line. If this holds, prepend
   `<a id="FRAGMENT-VERBATIM"></a>` to that row's first cell.
3. **Class D — de-anchor.** Neither holds. Drop the `#fragment`, keep the file link.

**Two exclusions that make rule 2 usable, both measured against this corpus:**

- **A changelog / revision-history row is never a Class-C anchor site.** Those tables record edit
  history, not the concept the fragment names; anchoring there produces a link that jumps to a
  provenance table. The mechanical token locator proposes exactly this for
  `docs/_glossary-android.md:331`, `docs/_glossary.md:285` and
  `docs/cross-platform/apple-business/01-role-permission-model.md:395`.

  `docs/android-lifecycle/02-provisioning-methods.md:45` already carries
  `<a id="byod-work-profile"></a>`, so the incoming `#byod` is a Class-B rewrite to
  `#byod-work-profile`, not a second anchor on the same row.
