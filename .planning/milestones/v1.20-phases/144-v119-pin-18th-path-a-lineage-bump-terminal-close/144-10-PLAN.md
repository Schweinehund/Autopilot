and scheduled runs under identical workflow names — one workflow has appeared as both, a day apart.

exactly 17 runs match. Fewer than 17 is a gap to report, not a set to work with.

Read back the SHA before reading any conclusion: assert every one of the 17 runs carries a head SHA
equal to the value recorded in Plan 09. This read-back is the whole point of the single-SHA rule —
the defective precedent it exists to prevent claimed a cross-OS exact match while the authoritative
SHA differed from the clone's.

Then take job-level JSON per run and record, per job: the workflow file, the run id, the job's
display name, and that job's own conclusion. Match on a stable SUBSTRING of the display name, never
on the YAML job key — the API surfaces the display string, and this project's job names deliberately
carry parenthetical detail. If any filter returns an empty set, treat it as a filter defect or a gap
and resolve it; never record it as an absence of failure.

Classify every skip:
  - the quarterly external-link job always skips under manual dispatch because its condition is
    scoped to the scheduled event. Derive the expected count by grepping the guard across all 17
    workflow files at this moment — two of them wrap the condition in an always-form, so a plain
    literal grep undercounts. Record the derived expected count and the observed count side by side.
  - a skip caused by the dependency on the harness job is a GAP. The new workflow's topology makes six
    such skips possible from a single harness failure, so name each one.
  - the advisory pin-helper job is NON-EVIDENCE regardless of its conclusion. Record it in its own
    column, never in the pass tally.

If any job is genuinely red, take exactly ONE remediation round: fix the cause, and note that a re-run
at a new SHA forces Axis-1 and Axis-3 to be re-run at that new SHA too. If a job is still red after
that round, STOP: record HARN-19 as UNMET with the failing job named, and do not proceed to Plan 11.
There is no fallback disposition — no carried item contains a CI-red-absorption clause, and
root-cause attribution does not turn a red job green.

Record the 17-row table, the skip ledger and the read-back result in `144-EVIDENCE.md`.
