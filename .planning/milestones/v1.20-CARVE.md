# v1.20-CARVE — Frozen-Surface Edit Authorization (Phases 139-144)

**Author:** Phase 139 Plan 01, Task 1 (D-01 through D-12, `139-CONTEXT.md`).
**Machine consumer:** `scripts/validation/carve-gate.mjs` parses the `carve-allowlist` fenced
block below. Everything else in this document is narrative for human readers and is not
parsed by any script.

## Purpose and span

This is the single, milestone-scoped authorization of record for every frozen-surface edit
landed in v1.20. It spans **Phases 139 through 144 inclusive** (D-04) — an owner-ratified
extension of the ROADMAP.md Phase 139 hard constraint, which previously read "Phases
139-143." Phase 144 makes the milestone's largest frozen-surface edits (the V119 pin, the new
`v1.20-milestone-audit.mjs` harness, apex chain regeneration, the 17th CI workflow) and would
otherwise be ungoverned by this contract.

Without this artifact, every subsequent edit to a frozen harness, workflow, or Pillar-C file
across Phases 139-144 is unauthorized. GOV-01's allowlist and the diff-based gate it feeds are
what make those edits legitimate.

## Naming

This artifact is named **`v1.20-CARVE`**, never `CARVE-1`. `CARVE-1` (and `CARVE-2`) are live
v1.18 Phase 133 tokens — `FROZEN-AWARE-ADOPTION-SWEEP-01`'s original routing name — that
v1.20's own REQUIREMENTS.md history cites and that this milestone is the one that *discharges*.
Reusing `CARVE-1` as this milestone's own artifact name would collide two distinct tokens in
one planning corpus and make the Phase 144 close audit ambiguous about which CARVE a grep hit
belongs to. This document never uses `CARVE-1` to refer to itself.

## Relationship to Phase 133's D-04

Phase 133 (v1.18) D-04 barred any workflow from setting a `ref:` to a milestone close SHA,
because a close-SHA checkout makes a frozen harness validate the frozen tree against itself —
a CI-layer masking bug, not real frozen-awareness.

**Phase 133's D-04 remains in force.** No workflow anywhere in this milestone may set a `ref:`
to a close SHA. This CARVE does **not** reverse that decision — it authorizes something
orthogonal: adding `fetch-depth: 0` to `actions/checkout@v4` steps changes what object graph is
available in the job's working copy; it does not touch `ref:`, and it does not make the
checkout point at any milestone close SHA. A workflow can carry `fetch-depth: 0` and still obey
D-04 completely, because the two settings govern unrelated axes of the checkout (depth of
history vs. which commit is checked out). Recording a "reversal" here would incorrectly put
authorization for close-SHA checkout into this governance artifact — that authorization does
not exist and this document must not create it.

## Scope exclusion

The gate's diff scope is `scripts/`, `.github/`, `docs/`, plus the two exact paths
`.gitattributes` and `package.json`. **`.planning/` is deliberately excluded from the gate's
scope** — including this file itself, the GOV-02 ledger, and every phase/plan artifact under
`.planning/`.

Two reasons, both load-bearing:

1. It makes `allowlist ⊆ narrative` true by construction — the allowlist is a subset of, and
   lives inside, the narrative document that authorizes it. If `.planning/` were in scope, this
   file would need to appear in its own allowlist to avoid failing its own gate, which is
   circular.
2. It keeps the gate from policing its own authorization artifact. A gate that could flag edits
   to the document that authorizes the gate would create exactly the self-referential failure
   mode GOV-01 exists to prevent (see the amendment procedure below, which is what actually
   governs edits to this file).

## Amendment procedure (D-09)

An amendment to the allowlist below is a commit that:

1. Touches **only** this file (`.planning/milestones/v1.20-CARVE.md`) — no other path, in-scope
   or out-of-scope, may be touched in the same commit.
2. Carries a one-line rationale for the addition, either in the commit message or as a new `#`
   comment line directly above the added glob(s) in the allowlist block.
3. Lands **before** the edit it authorizes — never in the same commit, never after.

This is what makes the allowlist non-self-authorizing: a blocked edit can never be cleared by
appending its own category to this file in the same commit as the edit. `carve-gate.mjs`
enforces rule 1 and 3 mechanically — see "Gate failure disposition" below — by failing any
commit (or dirty working tree) where this file and any in-scope path are touched together.

## Gate failure disposition (D-10)

- **Hard-block** on a non-zero `carve-gate.mjs` exit inside a plan's verification step. There is
  no warn-and-continue path.
- The `.claude/hooks/v1.20-carve-gate.cjs` Stop-hook nudges on the first fire and warns on
  subsequent fires for the same off-list set (D-08), as an early, session-level signal — it is
  advisory, not the enforcement mechanism itself.
- **The only resolution path for an off-list hit is a prior amendment commit** per the procedure
  above. A gate failure is never resolved by degrading it to a warning.
- **Gate failure is the expected steady state for Phases 140-143.** Those phases land
  frozen-surface edits whose categories are not yet enumerable today (D-03) — the gate will
  correctly report them off-list until each phase's plan lands its own amendment commit
  authorizing its category. This is by design, not a defect in the gate or the allowlist.

## GOV-02 grep procedure (D-12)

Every GOV-02 grep before editing a frozen validator line must be **target-scoped**, not
symbol-scoped: it must search for the **file path string**, not only the symbol/identifier
name. A symbol-only grep misses call sites that pin a *path literal* rather than a function or
constant name.

This is modelled on `check-phase-111.mjs`'s `V-111-TOOL03`, which pins
`check-phase-48.mjs`'s exact `{ n: 200, trim: false, prefix: '--self-test FAIL: ' }`
`execFailDetail(...)` call-site string verbatim via `String.includes()` — a plain substring
match, not an AST check or a regex with capture groups. Any edit to that exact text, even a
whitespace-only reformat, trips it.

The concrete example a symbol-only grep misses: `check-phase-66.mjs:42` holds
`const CI_WORKFLOW = '.github/workflows/audit-harness-v1.6-integrity.yml';` — a **file path
string**, not a function name. `V-66-05` asserts against that path literal. A grep for symbol
names like `PRED_BLOBS` or `V-69-08` would never surface this pinning; only a grep for the
literal path string `audit-harness-v1.6-integrity.yml` would. Before editing any frozen
validator or workflow file in this milestone, grep for both forms — the symbol AND the path
string — and record the result as a row in `.planning/milestones/v1.20-GOV-02-LEDGER.md`.
