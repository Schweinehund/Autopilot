    Create `scripts/pipeline/lib/ooxml.mjs` exporting exactly three named functions per D-05 and
    RESEARCH §Pattern 3: `extractEntry(docxPath, entryName)`, `extractBodyText(docxPath)`,
    `findHeadingStyleIds(docxPath)`. Import ONLY `readFileSync` from `node:fs` and `inflateRawSync`
    from `node:zlib` — zero external npm packages (the invariant that lets Phase 119 fold this into
    the validation chain without a new dependency). `extractEntry` walks ZIP local file headers by
    the `PK\x03\x04` signature, reads fileNameLength + extraFieldLength to locate dataStart, and for
    compression method 8 (DEFLATE) calls `inflateRawSync` on the compressed subarray; for method 0
    (Stored) returns the bytes directly; throws on any other method and on entry-not-found. CRITICAL
    per D-04/Pitfall 1: never call `toString('utf8')` on the raw .docx buffer and scan for text — the
    payload is DEFLATE-compressed, so a raw-byte scan is always false-green. `extractBodyText` pulls
    the `<w:body>...</w:body>` region from `word/document.xml`, strips XML tags, collapses whitespace,
    and applies CRLF→LF normalization to the inflated XML before matching. `findHeadingStyleIds`
    scans `word/document.xml` for `w:val="Heading1"`, `Heading2`, `Heading3` and returns the subset
    present. Add the data-descriptor safety guard from Pitfall 5: if compressedSize is 0 with method 8,
    skip that entry rather than crash. Use the RESEARCH JSDoc block on each export.
  </action>
  <verify>
    <automated>node --input-type=module -e "import('./scripts/pipeline/lib/ooxml.mjs').then(m => { const ok = ['extractEntry','extractBodyText','findHeadingStyleIds'].every(k => typeof m[k] === 'function'); process.exit(ok ? 0 : 1); })"</automated>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → local machine | pandoc MSI downloaded from GitHub crosses into the build environment |
| .docx file → OOXML helper | untrusted/compressed ZIP bytes are inflated and parsed by ooxml.mjs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-01 | Tampering | pandoc MSI supply chain | mitigate | Pin version to 3.7.0.2 from the official jgm/pandoc release URL; hard-assert `pandoc --version` == 3.7.0.2 before generating reference.docx; a mismatch aborts the task |
| T-113-02 | Denial of Service | ooxml.mjs inflateRawSync on a crafted ZIP (inflate amplification / zip-bomb) | mitigate | extractEntry reads a single named entry (word/document.xml or word/styles.xml), not the whole archive; add the Pitfall-5 data-descriptor guard (skip compressedSize===0 method-8 entries) so a malformed local header cannot loop or crash |
| T-113-03 | Tampering | ooxml.mjs path handling of docxPath input | mitigate | extractEntry only reads the caller-supplied path via readFileSync and matches an exact internal entry name; no path is derived from archive contents, so a malicious entry name cannot cause a path traversal write |
| T-113-SC | Tampering | Toolchain provenance (pandoc binary, not npm) | mitigate | Official GitHub release from primary author (RESEARCH Package Legitimacy Audit — no npm packages introduced); version-pin verification is the integrity gate. No package-manager install occurs, so no npm/pip/cargo legitimacy checkpoint is required. |
</threat_model>
