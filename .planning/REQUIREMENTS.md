# Requirements: v1.21 Enterprise Update, Driver & Firmware/BIOS Governance

**Defined:** 2026-08-19
**Core Value:** IT teams can independently provision, troubleshoot, and manage Windows, macOS, iOS/iPadOS, Android, and Linux devices through Microsoft Intune / Entra ID without escalating to engineering — and find those answers as clean, correctly-cited results in the Copilot Studio / SharePoint knowledge base. v1.21 extends that corpus from provisioning into **day-2 update governance** across operating systems, applications, drivers, firmware and BIOS.

**Milestone bar:** a five-platform enterprise update plan exists as both operations guides and one prescriptive Device Recipe, reachable through the `.docx` publish bundle; every enumerated corpus correction in the `FIX` category is landed with its governing validator still green; and both harness debts (`V120` back-anchor pin, C17 frozen-aware residue) are discharged with the apex green at close.

**Scope origin.** This milestone was scoped from a live corpus audit answering "do we have device configurations defined that create an enterprise-class update plan for OS, applications, drivers, firmware and BIOS?" `[MEASURED, 2026-08-19]` OS updates covered across 4 platforms; applications covered as **deployment only, not patching**; drivers and firmware sharing a single ~45-line disambiguation H2; **BIOS at zero coverage** (`DFCI`, `SEMM`, `Sure Admin`, `Dell Command`, `HP Connect`, `Think BIOS`, `hardwarePassword` all 0 occurrences corpus-wide); and **no configuration artifact of any kind** in the repository.

**Scope resolved via `/adversarial-review` (2026-08-19):** 5 parallel Finders → Adversary → Referee over 2,451 lines of research; **146 raw findings, 120 deduplicated, 3 full disprovals, 10 partials downgraded, ~107 confirmed**. The review caught **two fabricated citations**, a wrong publish-bundle canary literal, and a build-order recommendation that would have blinded this milestone's own verification harness. It also **dissolved six questions** that would otherwise have gone to the owner — most consequentially the enrolment binary, which was resolved by running the publish pipeline end to end rather than by argument. Four owner rulings were taken; all are recorded inline below. Every `[MEASURED]` figure was executed at HEAD `332ffc79` or earlier and is dated where it matters.

**Evidence labels.** `[MEASURED]` = a command was run against this repo, and it is named. `[SOURCED]` = a first-party page was fetched, with its own `ms.date`/`updated_at` recorded. `[UNVERIFIED]` = could not be confirmed; **must not be written as fact in any deliverable**. `[DIRECT]` vs `[RELAYED]` distinguishes quotes read as raw bytes from quotes relayed through a summarizing fetcher — introduced because two agents in this milestone each "re-fetched and verified" the same licence sentence and reached opposite conclusions, one having received a stale revision.

### BIOS — firmware and BIOS governance (BIOS)

**A three-way architecture split, not a three-way tool split.** `[MEASURED]` this is greenfield — zero corpus occurrences of every term. The discriminator is **who holds the BIOS secret and where the policy object lives**.

- [x] **BIOS-01**: `docs/operations/firmware-bios/00-overview.md` establishes the domain and routes by secret custody: **Dell** means Intune holds the secret (Graph `hardwarePasswordDetails`); **HP** means HP's cloud vault, outside the tenant; **Lenovo** means the customer holds it (encrypted INI or Azure Key Vault) — the only vendor where the signing key can live under the customer's own RBAC, logging and rotation.
- [x] **BIOS-02**: **Both** native Intune BIOS surfaces are documented **as disjoint**: **DFCI** (UEFI CSP, per-setting reporting, certificate trust chain) and **BIOS configuration and other settings** (a Templates policy, `.cctk` config file, 2 MB limit, **Dell only**). The v1.21 scoping named only one of them.
- [x] **BIOS-03**: DFCI OEM support is documented as **nine OEMs** (Acer, Asus, Dynabook, Fujitsu, Microsoft Surface, Panasonic, VAIO, Samsung, NEC) followed by the source's own *"Other OEMs are pending."*, with the six-OEM and one-OEM variants on two staler first-party pages recorded as a documented conflict. ## Out of Scope

Explicit boundaries with reasoning, to prevent re-adding.

- **RADIUS / NPS server-side build-out, network-switch configuration, and MAB** — carried from v1.14; infrastructure layer, not Intune device management.
- **Third-party patch-management products** (PatchMyPC, Ivanti and similar) — Enterprise App Catalog covers the documented need natively. **Discriminator for the whole vendor-tooling boundary:** a vendor tool is in scope **only if it is the only way to reach the capability through Intune**. Dell Command passes that test (the native policy cannot function without the agent); third-party patch products fail it.
- **Community WinGet automation frameworks** — not first-party, not Intune-shaped, and the sourced position is that WinGet is not an enterprise patching surface at all.
- **`winget configure` / DSC** — scoped by Microsoft to development-environment setup, never mentions Intune or MDM, and partial success is designed behaviour.
- **Vendor BIOS infrastructure Intune cannot reach**, and BIOS token tables / CMSL cmdlet syntax references / per-model matrices — the corpus constraint is Intune-delivery-shaped and link-not-copy. These guides route to vendor documentation; they do not rewrite vendor manuals.
- **WSUS / ConfigMgr server-side build-out** — the ConfigMgr **co-existence procedure** (DRV-06) is in scope because it is a first-party Intune-side configuration; standing up or operating the ConfigMgr infrastructure is not.
- **Retrofitting the 20 legacy `docs/operations/` documents to EEE / C17** — INT-02's ruling makes publish reach available without it. The retrofit remains available to a future hygiene milestone.
- **Full Azure AI Search structured index, SharePoint content approval, and Graph-API auto-upload of the publish bundle** — infra/deployment levers carried from earlier milestones; the last would introduce the first `secrets.` reference in any workflow in this repository.
